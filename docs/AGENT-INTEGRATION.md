# Встраивание проверки разрешений в клиент (агент)

Автор: SecretHero. Состояние: **план; в клиент ничего не встроено** (этап 0.5.2, часть про агента).

## Зачем

Сервер управления выдаёт подписанные разрешения на сеанс, а библиотека `zherodizk-grant` умеет их проверять.
Пока агент (управляемая сторона клиента) их не требует, любой, кто знает ID и пароль устройства, подключается
напрямую и обходит все правила. Защита начинает работать только когда агент **отказывает без валидного
разрешения** на любом пути соединения — прямом и через ретранслятор.

## Что должен делать агент

1. При регистрации получить и сохранить: идентификатор организации, идентификатор устройства, публичный ключ
   подписи разрешений сервера (один или несколько — ротация).
2. При каждом входящем запросе соединения взять токен разрешения из запроса оператора.
3. `verify(token, доверенные_ключи, now, свой_device_id)` → `ReplayCache::accept` →
   `authorize_connection(claims, LocalState, запрошенные_права, now)`.
4. Отказать при любой ошибке; показывать пользователю согласие (в режиме «с присутствием») и учитывать
   локальные ограничения владельца.
5. Не разрешать вход по постоянному паролю в управляемом режиме (этап 0.5.3).
6. Держать список отозванных разрешений и прекращать активные сеансы при отзыве или потере связи (0.5.4).

## Что мешает сделать это сразу

- Клиент собирается командой `cargo build --locked`; подключение наших крейтов требует изменить его
  `Cargo.toml`/`Cargo.lock` теми же воспроизводимыми заменами, что и остальная идентичность.
- Нужно найти единственную точку принятия соединения в исходном клиенте (и для прямого, и для relay-пути) и
  убедиться, что обходных путей нет (в том числе «быстрые» режимы, файловый менеджер, терминал, порт-форвардинг).
- Проверка возможна только на двух реальных машинах: CI не запускает графический клиент и не устанавливает соединений.
- Протокол обмена токеном между оператором и агентом нужно добавить в сообщения клиента (изменение схемы протокола).

## План работы

1. Прочитать и описать точки входа соединения в закреплённой версии клиента (только чтение, без правок).
2. Добавить манифестом замен подключение крейтов и вызов проверки в этих точках; сборка в CI должна проходить.
3. Добавить в клиент оператора получение разрешения у сервера управления.
4. Испытать на стенде: соединение с валидным, просроченным, отозванным, повторным и чужим разрешением;
   прямой и relay-путь; Windows ↔ Linux.

До завершения этих шагов в README и дорожной карте управляемые сеансы остаются неготовыми.

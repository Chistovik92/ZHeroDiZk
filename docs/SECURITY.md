# Безопасность текущего пакета

Этот пакет не слушает сетевые порты, не даёт удалённый доступ и не изменяет
установленные сторонние клиенты. Нельзя представлять policy crate как готовую защиту.

## Угрозы и следующие обязательные проверки

- Подмена разрешения: стандартные криптографические библиотеки, проверка подписи,
  аудитории/ключа/версии, отрицательные тесты, запрет неизвестных алгоритмов.
- Повторное использование: одноразовый nonce и привязка к сеансу, ключам и каналу.
- Повышение привилегий: пересечение серверного, выданного и локального набора прав.
- Межорганизационный доступ: изоляция в БД и в агенте, отрицательные API-тесты.
- Обход панели: проверка прав в агенте для каждого пути установления соединения.
- Отзыв: завершение потоков, запрет продления, проверка при потере сети.
- Компрометация обновлений: подписи, отдельные офлайн-ключи, защита от отката.
- Системная служба: минимальные привилегии, проверенный IPC, без запуска всего UI root.
- Журналы: не писать токены/пароли/содержимое буфера; явно задавать сроки хранения.

## Известные проблемы текущей сборки клиента

- Исходный клиент по умолчанию использовал встроенный адрес и открытый ключ публичного сервера исходного
  проекта, его API и сервис проверки обновлений (при этом отправлялся отпечаток устройства). **Исправлено
  в 0.4.0 (пункт 0.3.7)**: адреса и ключ убраны, проверка обновлений отключена; сборки Linux и Windows
  проверяют отсутствие этих строк в бинарниках (`tools/check_client_network.py`):
  Linux https://github.com/Chistovik92/ZHeroDiZk/actions/runs/37081370611, Windows https://github.com/Chistovik92/ZHeroDiZk/actions/runs/37081373712.
- **Остаётся:** клиент использует публичные STUN-серверы (Google, Cloudflare, Nextcloud) для определения типа NAT —
  им виден IP-адрес клиента; при IPv6-only сетях возможен запрос к сервису nip.io; ссылки в интерфейсе ведут на сайт
  исходного проекта (замена — пункт 0.2.4). Без запуска клиента на стенде это не проверено в работе, только по коду.
- Бинарники клиентов всё равно не публикуются до закрытия остальных условий выпуска.
- В сборке сервера ZHeroDiZk проверка обновлений на стороннем сервере удалена.

## Сервер управления (0.4.0): модель и ограничения

Защищено и проверено тестами: хэширование паролей Argon2id; хранение только SHA-256 токенов сессий и регистрации;
одинаковый ответ на неверный пароль, неизвестную учётку и блокировку; блокировка после 5 неудач на 15 минут;
TOTP с запретом повторного использования шага и резервными кодами; шифрование секретов MFA (ключ `ZHD_MFA_KEY`);
проверка владения ключом устройства до траты токена; доступ запрещён без явного правила; изоляция организаций
(в запросах и в БД); журнал аудита без секретов и без возможности правки.

**Добавлено в 0.4.7–0.4.8:** ограничение частоты анонимных запросов по адресу клиента (429 с `Retry-After`; за обратным прокси —
по `X-Forwarded-For`, только при `ZHD_TRUST_FORWARDED_FOR=true`); юнит systemd с `NoNewPrivileges`, `ProtectSystem=strict`,
пустым набором прав, фильтром системных вызовов и `UMask=0077`; файл настроек с секретами доступен только root и группе сервиса.

**Не защищено / не сделано** (риски для эксплуатации): сервер не терминирует TLS — только за обратным прокси с TLS
(примеры Caddy и nginx в пакете), иначе пароли и токены идут открытым текстом; блокировка учётки при подборе пароля
может использоваться для намеренного досаждения; соединение с PostgreSQL не шифруется (база должна быть на том же хосте
или в доверенной сети); регистрация первого администратора открыта любому, кто первым дотянется до
сервера (по умолчанию слушает только 127.0.0.1); нет смены и сброса пароля, отзыва всех сессий, удаления учёток;
запись аудита не всегда в одной транзакции с действием; нет ротации ключа `ZHD_MFA_KEY`; независимого аудита
безопасности не было.

## Разрешения на сеанс (0.5.1): модель и ограничения

Проверено тестами: подпись Ed25519 над точным текстом токена; несколько доверенных ключей (ротация); отказ при чужом
ключе, подмене содержимого и идентификатора ключа, неизвестных полях; срок жизни ограничен на устройстве;
привязка к одному устройству; защита от повтора (`ReplayCache`); выдача только в пределах ACL и только для активного
устройства; токен не хранится и не попадает в журнал; БД не допускает разрешений между организациями.

**Ограничения:** агент (клиент) пока не требует разрешений, поэтому защита от прямого подключения в
собранных клиентах не работает; список отзыва на устройства не доставляется; нет аренды активного сеанса;
ключ подписи `ZHD_GRANT_KEY` хранится в окружении сервера (компрометация позволяет выдавать любые разрешения);
публичный ключ устройству пока передаётся вручную; ротация ключа подписи не автоматизирована.

## Уже реализованные меры

Doctor только читает окружение. Пробная загрузка libxdo вынесена в подпроцесс,
таймаут 5 секунд; крах нативного загрузчика не должен убить основной отчёт.
Он проверяет библиотеку, но не делает кликов и не подключается к X-серверу.
В Simply случай libxdot.so.4 не считается наличием libxdo.so.3.

Bootstrap использует аргументы subprocess без shell. Новый каталог создаётся
эксклюзивно, существующие исходники не сбрасываются и не удаляются. SHA проверяется
после checkout. Подмодули берутся из закреплённого upstream; их полная доступность,
лицензии и безопасность требуют отдельной проверки перед выпуском бинарника.

Сейчас нет процедуры приёма приватных отчётов: публичный выпуск не сделан.
Перед выпуском добавить рабочий контакт, сроки реакции и процесс security releases.

# Архитектура ZHeroDiZk

Автор: SecretHero. Структура репозитория — [PROJECT-STRUCTURE.md](PROJECT-STRUCTURE.md), платформы — [PLATFORMS.md](PLATFORMS.md).

Цель: самостоятельное развёртывание, открытые исходники всех компонентов, единая
редакция без платных лимитов. Цена эксплуатации серверов и трафика не исчезает.

## Компоненты и статус

| Компонент | Технология | Статус |
|---|---|---|
| Клиент/агент | Rust + Flutter, адаптированный исходный клиент | Linux и Windows собираются в CI со своей идентичностью и без чужих адресов по умолчанию; остальные платформы не начаты |
| Policy | Rust, без зависимостей | 17 unit-тестов прошли в CI исходной основы |
| Диагностика Linux | Python stdlib | работает, тестируется |
| Control API (`crates/control`) | Rust, axum, sqlx | аккаунты, MFA, организации, устройства, ACL, аудит — готово и проверено в CI (0.4.0); выдача разрешений на сеанс — 0.5.0 |
| База | PostgreSQL 16 | схема из 6 миграций, проверена в CI |
| Админ-панель | TypeScript/React | проектирование |
| Rendezvous/relay | адаптация открытых серверных компонентов (`zhd-rendezvous`, `zhd-relay`) | собираются, пакеты и Docker проверены (0.3.x) |
| Подписанные обновления | отдельные ключи выпуска | проектирование |

Текущая основа платформы находится в Chistovik92/ZHeroDiZk.
Клиент, транспорт и платформа остаются отдельными архитектурными компонентами;
выделение их в отдельные репозитории решается по мере реализации.
Модуль правил доступа называется zherodizk-access-policy.

## Контур доступа

Регистрация устройства → доказательство владения ключом → привязка к организации.
Оператор → вход/MFA → проверка ACL → короткоживущее подписанное разрешение.
Агент → проверка подписи, аудитории, идентификаторов и срока → локальные ограничения
и согласие → согласование криптографического сеанса → ввод/экран/файлы.

Policy crate вызывается только ПОСЛЕ проверки подписи и получения доверенных данных.
Поля Context не являются форматом сетевого API и не должны поступать напрямую
от клиента. Часы и состояние отзыва задаёт доверенная сторона.

Отзыв: контрольный канал плюс ограниченная аренда активного сеанса; при отсутствии
продления вход и передача данных прекращаются в пределах заданного срока.
Периодические проверки, доставка отзыва и остановка потоков пока не реализованы.

Прямой и ретранслируемый путь должны проходить одинаковую проверку на агенте.
Запрет только в веб-панели или relay можно обойти прямым подключением.
Управляемый режим должен исключать обход через прежний постоянный пароль.
Совместимость со стандартными клиентами исходного проекта не обещается после включения
обязательных управляемых разрешений.

Сервер управления не получает экран/буфер обмена. Relay передаёт зашифрованный
поток без ключей содержимого. Он видит метаданные. Доверие к ключам устройств
и ротация должны быть спроектированы против подмены сервером управления.

## Сервер управления (0.4.0)

Модули `crates/control/src`: `config` (окружение), `password` (Argon2id), `auth` (аккаунты, сессии, MFA),
`totp`, `crypto` (AES-256-GCM для секретов), `orgs` (организации, роли, токены регистрации),
`devices` (регистрация с проверкой ключа Ed25519), `groups` (группы, ACL, адресная книга), `audit`.
Описание интерфейса — [api/openapi.yaml](api/openapi.yaml).

Принципы: доступ запрещён, пока правило его не даёт (роль владельца сама по себе не открывает устройства);
организация проверяется в каждом запросе, а целостность связей между организациями дополнительно
обеспечивается составными внешними ключами БД; посторонний получает 404, а не 403; токены и коды хранятся
только в виде хэшей, секреты MFA — в зашифрованном виде; журнал аудита нельзя изменить даже запросом к БД.
`effective_capabilities` вычисляет итоговые права пользователя на устройство и станет входом для
модуля `access-policy` на этапе 0.5.0.

## Сущности БД (фактическая схема на 0.4.0)

users, sessions, recovery_codes, organizations, memberships, enrollment_tokens, devices, device_groups,
device_group_members, acl_rules, address_book_entries, audit_events. Миграции — `crates/control/migrations`.

## Сущности будущей БД (план)

organizations, users, memberships, devices, device_keys, device_groups,
address_books, policies, session_grants, sessions, revocations, audit_events,
relay_nodes, releases. Проверка tenant обязательна в каждом запросе.
Ни одной миграции ещё нет; не считать эту схему действующим хранилищем.

## Ограничения среды

Linux X11, Wayland, Windows UAC/lock screen, macOS permissions и Android input
проверяются отдельно. Поддержка Flutter не означает одинаковый удалённый ввод.
Первая вертикаль: Windows ↔ Windows, затем обязательная регрессия Simply/X11.
Браузерный клиент — отдельный этап после нативного сеанса и панели управления.
